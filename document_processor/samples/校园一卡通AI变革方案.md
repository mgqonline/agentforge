## 一、背景与现状诊断

### 1.1 老项目典型痛点

| 维度 | 现状问题 | 影响 |
|------|----------|------|
| 系统架构 | 烟囱式孤岛，与图书馆、宿管、教务系统割裂 | 数据无法流通，服务体验割裂 |
| 数据资产 | 沉淀海量交易流水，但仅用于对账统计 | 巨大数据价值白白浪费 |
| 安全能力 | 依赖物理卡 + 密码，规则型风控滞后 | 盗刷、借卡事件频发 |
| 服务体验 | 人工窗口处理挂失/查询，响应慢 | 师生满意度低 |
| 运营决策 | 依赖人工报表，滞后 1～7 天 | 管理层无法及时响应异常 |
| 商业模式 | 以系统建设费 + 通道费为主，增长空间有限 | 收入天花板低，同质化竞争 |

### 1.2 数据资产盘点

一卡通系统天然沉淀以下高价值数据：

- **消费行为数据**：时间、地点、金额、商户类型，每生每天产生 3～15 条记录
- **门禁通行数据**：出入宿舍楼、教学楼、实验室的时序轨迹
- **身份认证数据**：刷卡频次、设备绑定、人脸识别记录
- **余额充值数据**：充值周期、金额分布、来源渠道
- **设备状态数据**：终端在线率、故障记录、流量峰谷

这些数据维度交叉，可以刻画出极为精准的**学生生活画像**与**校园运营全貌**，是 AI 改造的核心原料。

## 二、整体战略框架

### 2.1 核心战略定位

> 将校园一卡通从「交易收单工具」升级为「校园智慧运营中枢」

```
原有定位：支付工具 → 目标定位：校园数字神经中枢
         ↓
  数据 × AI → 安全 + 服务 + 决策 + 生态
```

### 2.2 价值主张

- **对学校**：提升校园安全、辅助管理决策、降低运营成本
- **对师生**：提升服务体验、获得个性化关怀与便利
- **对商户**：精准营销、经营洞察、降低损耗
- **对运营方**：扩大收入边界、构建数据护城河

### 2.3 改造原则

1. **稳定优先**：采用旁路接入而非推倒重建，不影响核心交易链路
2. **数据合规**：先建授权体系，再开放数据能力
3. **渐进迭代**：从低风险场景切入，验证后再扩展
4. **体验驱动**：每个 AI 能力都要有可感知的师生体验提升
5. **可解释 AI**：关键决策（如风险拦截、困难生识别）须有可追溯依据

## 三、四大 AI 能力方向

### 3.1 智能风控与安全

#### 3.1.1 行为基线建模

为每个用户建立个性化正常行为模型，包含：

- 常用消费时段（早中晚餐时间窗、作息规律）
- 常用消费地点（食堂楼层、常去商户）
- 单次消费金额分布（均值、方差）
- 设备使用习惯（常用读卡器、手机端操作频率）

**技术实现**：

```
数据采集 → 特征工程（滑动窗口统计）
        → 无监督聚类（K-Means / DBSCAN）
        → 个人基线建模（自回归 + 统计阈值）
        → 在线异常评分
```

#### 3.1.2 实时风险预警

| 风险类型 | 触发条件 | 处置动作 |
|----------|----------|----------|
| 异地消费 | 30 分钟内出现地理位置矛盾的两笔消费 | 短信通知 + 要求二次确认 |
| 金额突变 | 单笔金额超过历史均值 5 倍 | 弹出人脸核验 |
| 频率异常 | 1 小时内同一设备刷卡 10 次以上 | 临时冻结 + 通知管理员 |
| 深夜高额 | 23:00～6:00 单笔超 200 元 | 短信预警 + 延迟到账 |
| 长期未使用后突然活跃 | 30 天不活跃后突然高频刷卡 | 身份重新核验 |

#### 3.1.3 多因子生物认证

**演进路径**：

```
阶段一：人脸识别辅助核验（高风险交易触发）
阶段二：人脸 + 步态双因子（门禁场景）
阶段三：无感通行（行人重识别 + 动态授权）
```

**关键技术选型**：
- 本地推理优先（边缘 AI 芯片），降低网络依赖
- 活体检测必须，防照片/视频攻击
- 差分隐私存储生物特征模板

### 3.2 个性化运营服务

#### 3.2.1 学生用户画像体系

构建多维度标签体系：

```
基础属性层：年级、院系、宿舍区域
行为特征层：
  - 消费习惯（食堂偏好、消费时段、月均支出）
  - 活跃程度（日均刷卡次数、活跃天数）
  - 社交属性（常见拼桌时段、群体特征）
状态感知层：
  - 经济状况（余额水位、充值频率、申请补贴记录）
  - 生活规律（作息是否规律、饮食结构异常）
  - 情绪健康（消费断崖式下降、深夜高频外卖）
```

#### 3.2.2 精准关怀预警

> 重要：此功能涉及学生隐私，必须在学校授权且符合法规前提下开展

**困难生识别模型**：

触发条件组合（满足 2 项以上自动生成关怀工单）：
- 连续 7 天日均消费低于 15 元
- 近 30 天充值频率/金额显著下降
- 消费时段集中在最便宜的早餐时段
- 未申请校内助学金但消费特征匹配

输出：学工处系统接收工单，由人工判断是否介入，AI 仅做识别不做最终处置。

**心理健康预警（辅助指标）**：
- 作息紊乱（连续 5 天凌晨消费）
- 社交隔离（周末宿舍门禁未外出）
- 消费结构剧变（餐饮消费骤降、大量购买能量饮料）

#### 3.2.3 商户智能推荐

```
用户维度：根据历史偏好 + 当前时段 + 余额水平
商户维度：库存水平 + 当日流量预测 + 优惠活动
环境维度：天气、节假日、考试周

→ 个性化 Push（App/微信服务号）
→ 入场引导屏精准展示
→ 余额不足时的消费降级建议
```

#### 3.2.4 AI 智能客服

覆盖高频问题（占人工咨询量约 70%）：

| 问题类型 | AI 处理方式 |
|----------|-------------|
| 挂失补卡 | 自助流程引导 + 临时数字卡签发 |
| 余额查询/明细 | 直接返回 + 异常消费标注 |
| 充值失败 | 自动诊断（余额、网络、限额）|
| 商户投诉 | 自动记录 + 分发 + 进度跟踪 |
| 退款申请 | 规则判断 + 自动审批（小额）|

**NLP 技术**：接入开源大语言模型（如 Qwen / ChatGLM），本地化部署，训练校园专业语料。

### 3.3 智慧校园数据中台

#### 3.3.1 系统联动矩阵

| 接入系统 | 数据互通内容 | 联动价值 |
|----------|--------------|----------|
| 图书馆系统 | 借阅记录、进馆时长 | 学习行为画像、座位推荐 |
| 宿管系统 | 出入时间、访客记录 | 安全预警、夜不归宿提醒 |
| 教务系统 | 课表、成绩、出勤 | 消费-学业相关性分析 |
| 医务室 | 就诊记录（脱敏） | 健康状态感知 |
| 体育场馆 | 预约、使用记录 | 运动行为分析 |
| 外卖/电商平台 | 校内配送数据 | 消费全量还原 |

#### 3.3.2 能耗智能优化

**场景**：利用门禁 + 消费数据预测教室、食堂、宿舍楼的人流密度，联动楼宇控制系统。

```
数据输入：
  - 历史人流热力图（按小时、按区域）
  - 课表数据（预期人流）
  - 天气数据（影响通勤行为）

模型输出：
  - 未来 2 小时各区域人流预测
  - 空调/照明开启建议
  - 食堂备餐量建议

预期效益：
  - 食堂餐品浪费降低 20%～35%
  - 楼宇能耗降低 10%～18%
```

#### 3.3.3 校园安防联动

```
触发条件：
  - 非工作时间进入实验室（刷卡 + 人脸不一致）
  - 陌生人持卡进入封闭区域
  - 宿舍楼深夜群体异常聚集

联动动作：
  - 安保中心实时推送告警
  - 摄像头定向调取
  - 电话核实责任人
```

### 3.4 数据决策支撑

#### 3.4.1 经营管理 AI 看板

**面向校方管理层**：

```
校长/副校长看板：
  └── 全校人流热力（实时）
  └── 本月消费总量同比/环比
  └── 安全事件摘要
  └── 困难生关怀进度

后勤部门看板：
  └── 各食堂今日营业额排名
  └── 浪费指数（备餐量与售出差值）
  └── 设备故障率地图
  └── 能耗对比（本校 vs 历史 vs 同类型校）

学工部门看板：
  └── 关怀工单处理进度
  └── 心理预警人数趋势
  └── 奖助学金覆盖率分析
```

#### 3.4.2 商户经营洞察

**面向校内商户运营者**：

- 客流预测（明天预计到访 X 人，高峰时段 11:30～12:30）
- 菜品销量排行 + 退出建议
- 顾客复购率分析
- 对标分析（与同类食堂对比）

#### 3.4.3 预测分析模型

| 预测场景 | 模型类型 | 输出 |
|----------|----------|------|
| 期末消费预测 | 时序预测（LSTM） | 充值引导时机、备货建议 |
| 新生消费能力评估 | 回归模型 | 精准资助政策制定 |
| 设备故障预测 | 异常检测 | 预防性维护工单 |
| 商户收入预测 | 多因子回归 | 合同谈判、租金定价 |

## 四、技术架构设计

### 4.1 整体架构（边车模式）

```
┌─────────────────────────────────────┐
│          现有核心交易系统              │  ← 不动，保持稳定
│   POS 终端 → 交易中台 → 财务清算      │
└──────────────┬──────────────────────┘
               │ 消息队列（Kafka）旁路监听
               ▼
┌─────────────────────────────────────┐
│            AI 能力层（新建）          │
│  ┌─────────┐ ┌─────────┐ ┌────────┐│
│  │ 风控引擎 │ │ 推荐引擎 │ │ NLP客服││
│  └─────────┘ └─────────┘ └────────┘│
│  ┌─────────────────────────────────┐│
│  │        特征工程平台              ││
│  └─────────────────────────────────┘│
│  ┌─────────────────────────────────┐│
│  │        数据湖（离线+实时）        ││
│  └─────────────────────────────────┘│
└──────────────┬──────────────────────┘
               │ API / 事件回写
               ▼
┌─────────────────────────────────────┐
│          应用层（面向用户）            │
│  管理看板  ·  小程序  ·  学工系统     │
└─────────────────────────────────────┘
```

### 4.2 关键技术选型

| 层次 | 组件 | 推荐选型 | 理由 |
|------|------|----------|------|
| 消息队列 | 事件流 | Apache Kafka | 高吞吐，与现有系统解耦 |
| 数据存储 | 离线数仓 | ClickHouse / Doris | 列存，OLAP 查询快 |
| 数据存储 | 实时流 | Apache Flink | 毫秒级风控计算 |
| 特征平台 | Feature Store | Feast（开源） | 统一管理离线/在线特征 |
| 模型训练 | ML 平台 | MLflow + 私有化 GPU | 模型版本管理 |
| 模型推理 | 在线服务 | Triton Inference Server | 低延迟、高并发 |
| NLP 基座 | 大模型 | Qwen2 / ChatGLM（私有部署） | 数据不出校 |
| 人脸识别 | 边缘 AI | 海康 / 旷视 SDK + 边缘芯片 | 本地推理，低延迟 |
| 监控告警 | 可观测性 | Prometheus + Grafana | 模型漂移、延迟监控 |

### 4.3 数据安全设计

```
数据分级：
  L1 - 公开数据（汇总统计）：无限制访问
  L2 - 内部数据（脱敏行为数据）：授权研究人员
  L3 - 敏感数据（个人身份 + 消费明细）：最小权限原则
  L4 - 高敏数据（生物特征）：本地存储，禁止外传

技术措施：
  - 数据传输：TLS 1.3 全程加密
  - 存储加密：AES-256
  - 生物特征：不可逆特征向量存储（非原始图像）
  - 访问审计：全链路操作日志，保留 180 天
  - 差分隐私：对外提供统计数据时添加噪声
```

## 五、三阶段推进路径

### 第一阶段：夯基础（0～6 个月）

**核心目标**：把数据资产盘清楚，搭好 AI 基础设施

| 任务 | 负责方 | 产出物 |
|------|--------|--------|
| 历史数据清洗与标准化 | 数据团队 | 标准化数据集 |
| 数据仓库搭建 | 基础设施团队 | 离线数仓上线 |
| 消息队列接入（旁路） | 后端团队 | Kafka 实时数据流 |
| 隐私合规评估 | 法务 + 产品 | 合规报告 + 数据使用协议 |
| AI 基础设施选型采购 | 架构团队 | 技术方案确认 |
| 特征工程平台 MVP | 算法团队 | 核心特征上线 |
| 学生数据授权机制 | 产品 + 法务 | 授权弹窗 + 协议文本 |

**里程碑**：完成 3 年历史数据入仓，实时数据流 P99 延迟 < 500ms

---

### 第二阶段：建能力（6～18 个月）

**核心目标**：核心 AI 能力上线，产生可感知价值

| 时间节点 | 上线能力 | 验证指标 |
|----------|----------|----------|
| M6～M8 | 异常交易实时预警 | 误报率 < 5%，漏报率 < 2% |
| M8～M10 | AI 智能客服（文字） | 自助解决率 > 60% |
| M10～M12 | 个性化消费推荐 | 推荐点击率 > 8% |
| M12～M14 | 困难生关怀预警 | 与学工部门人工核实准确率 > 75% |
| M14～M16 | 经营分析看板 | 管理层周活跃使用率 > 80% |
| M16～M18 | 能耗预测与优化 | 食堂浪费率下降 > 15% |

**关键风险与应对**：

| 风险 | 概率 | 应对措施 |
|------|------|----------|
| 数据质量差导致模型效果差 | 高 | 第一阶段严格数据治理，设置质量门禁 |
| 学校/学生对数据使用抵触 | 中 | 透明化数据使用说明，提供退出机制 |
| 旧系统接口不稳定 | 中 | 旁路设计 + 断路器模式，不影响主链路 |
| AI 风控误拦截影响用户体验 | 中 | 先以"通知"代替"拦截"，逐步收紧阈值 |

---

### 第三阶段：深融合（18 个月+）

**核心目标**：构建差异化护城河，探索新业务模式

- 建立跨校数据联邦（在隐私保护前提下），输出行业级洞察
- AI 中台能力产品化，向中小学校/职校 SaaS 化输出
- 构建校园商业生态（基于用户画像的精准广告/联名活动）
- 探索「校园钱包」延伸：校外消费、校园贷款替代品、奖学金理财

## 六、核心约束与风险管控

### 6.1 隐私合规红线

- **严格遵守**：《个人信息保护法》《数据安全法》《网络安全法》
- **生物特征**：须单独告知并取得明确授权，不得用于商业目的
- **未成年人**：K12 场景须获得家长授权，数据处理更为严格
- **数据共享**：校内跨系统共享须脱敏处理，对外提供仅限聚合统计
- **删除权**：学生毕业后 1 年内完成个人数据匿名化处理

### 6.2 AI 决策伦理准则

1. **困难生识别**：AI 仅提供候选名单，最终判断必须由人工完成
2. **风控拦截**：拦截动作须有申诉通道，48 小时内人工处理
3. **推荐系统**：不得推荐可能诱导过度消费的内容给低余额用户
4. **差异化服务**：AI 能力不得造成服务歧视，基础功能对所有用户一致

### 6.3 系统稳定性保障

```
核心交易链路 SLA：99.99%（每年不超过 52 分钟停机）
AI 能力层 SLA：99.9%（降级时核心交易不受影响）

降级策略：
  - AI 风控不可用时 → 回退到规则引擎
  - 推荐服务不可用时 → 展示默认内容
  - 看板服务不可用时 → 展示昨日缓存数据
```

## 七、商业模式创新

### 7.1 收入结构演进

### 启动前必做（第 0 个月）

### 第一个 AI 功能建议

**推荐从「异常消费短信预警」开始**，原因：
1. 技术难度低（规则 + 简单异常检测即可）
2. 对核心系统无改造风险
3. 学生和学校都能直接感受到价值
4. 数据合规风险低（通知型，非拦截型）
5. 可在 6～8 周内上线，快速验证 AI 改造路径
