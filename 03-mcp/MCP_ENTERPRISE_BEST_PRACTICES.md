# 企业级 MCP 工具集封装规范

将公司内部庞杂的业务系统（如 ERP、CRM、财务系统）开放给 AI 大模型使用时，**绝不能直接裸露底层 API**。必须在两者之间架设一道 **MCP (Model Context Protocol) 统一防线**。

## 一、为什么要做企业级封装？（核心痛点）

1. **大模型的“幻觉”与不可控性**：AI 有时候会乱编参数（比如退款金额瞎填个 -100，或者把订单号格式搞错）。
2. **越权访问的灾难**：如果大模型代表客服A在操作，如果不做拦截，它就有可能跨越权限去调用财务B的审批接口。
3. **乱七八糟的底层报错**：如果底层 Java 接口直接抛一个 `NullPointerException` 或者 HTTP 500 页面给大模型，模型会瞬间懵逼并导致系统崩溃。

## 二、企业级封装的“三道防线”

参考 [03_enterprise_mcp_server.py](file:///Users/mac/Documents/project/ailearning/03-mcp/03_enterprise_mcp_server.py) 中的实战代码，我们在把底层 API 包装成 MCP 工具时，必须建立以下三道防线：

### 第一道防线：参数极致校验 (Pydantic 拦截)
大模型天生不擅长写精确格式的数据。
* **做法**：强制使用 `Pydantic` 等强类型校验库。对于订单号、金额等字段，必须在 Schema 中用正则表达式（如 `pattern=r"^ORD-\d{6}$"`）和数值边界（如 `gt=0`）死死卡住。
* **效果**：大模型参数一旦写错，在踏入内网真实系统前就会被直接弹回，既保护了底层系统，又能通过精准的报错信息促使大模型重试纠错。

### 第二道防线：权限隔离验证 (IAM / RBAC)
**MCP 工具是不认人的，但背后的操作者是有身份的。**
* **做法**：工具的入参中必须隐式要求传递当前操作者的 `User Context`（比如 JWT Token）。在执行高危操作（退款、删库、发邮件）前，MCP 网关必须去鉴权中心核实该 Token 是否有相应权限（Role）。
* **效果**：即使用户在对话框里恶意通过 Prompt 诱导大模型（Prompt Injection）去越权退款，也会在这一层被物理拦截。

### 第三道防线：统一的错误码规范 (Standardized Error Code)
大模型是依靠文字来推理的机器。
* **做法**：永远不要把 HTML 错误页或底层的 Stack Trace 扔给大模型。统一封装 `{"code": 401, "msg": "鉴权失败", "data": {}}` 这样的标准 JSON 返回。
* **好处**：大模型看到 `code: 400` 和清晰的 `msg` 时，它内置的 **ReAct / Reflection 范式**会立刻明白：“哦，我刚才的金额填错了，我改一下再调一次”。这赋予了 Agent 自我修复的能力！

## 三、部署与架构演进建议

在真正的生产环境中，建议遵循以下架构选型：
1. **防线前置**：在企业内网单独搭建一个 `MCP Gateway` 服务，它负责扛住所有大模型的工具调用流量，在这里统一做日志落盘审计。
2. **读写分离封装**：对于查询类工具（Read），尽量放宽约束；对于变更类工具（Write/Refund），不仅要严格鉴权，最好配合 `Human-in-the-loop (人机协同)`，在大模型调用前，在前端页面弹窗让真管人员点一下“批准”再放行。
