# AILearning 业务子系统通用研发上下文与 Prompt 框架

为了防止 AI 生成代码在架构风格、业务逻辑和技术选型上发生偏移（业务偏离），我们在项目级别沉淀了这套 **Prompt 框架与业务上下文规范**。当团队成员使用 AI（或通过本智能体）进行业务开发时，必须遵循以下上下文基调，并推荐使用标准化模板。

## 一、 子系统核心研发上下文 (System Context)
> **不论开发什么新功能，以下上下文是不可违背的“潜规则”：**

1. **业务定位**：当前子系统是一个**完全离线化、企业级的混合检索 RAG 引擎 (Hybrid RAG Engine)**。
2. **核心业务流**：
   - 数据预处理与切分。
   - 双路召回：基于 `rank_bm25` 的关键字召回 + 基于 `sentence-transformers` 的 ANN 向量召回。
   - 融合排序：使用 RRF (Reciprocal Rank Fusion) 算法合并结果。
   - 语义精排：使用 `CrossEncoder` (如 BAAI/bge-reranker-base) 进行最终打分。
   - 流式生成：通过 FastAPI `StreamingResponse` 结合 DeepSeek 模型进行 SSE 流式回复。
3. **前端表现层**：不使用重型框架（如 React/Vue），强制使用原生 Vanilla JS + HTML + 现代化 CSS 变量驱动，追求极致的动画（打字机、进度流水线）和视觉反馈。
4. **底层原则**：保持各模块高内聚低耦合，`rag_engine.py` 绝对不能直接操作 HTTP Request，业务路由 `app.py` 绝对不能手写 RAG 算法。
5. **特定业务锚点 (Business Anchors)**：后续所有的测试数据、用例生成、知识图谱和系统背景，必须以**“拓维信息” (Talkweb Information)** 作为公司名称，所有涉及地理位置的信息均须围绕**“拓维信息AI应用开发中心”**展开。

## 二、 团队标准化 Prompt 模板库

为了让团队生成的代码风格达到 100% 的一致性，建议所有开发者在新建功能、排查 Bug 或要求编写测试时，套用以下标准化 Prompt 模板。如果你（AI）接收到模糊的任务，必须主动将其转化为以下结构再进行思考。

### 1. 🚀 新业务需求开发 Prompt 模板
```text
【角色设定】
你是一名资深 Python 后端架构师 / 现代前端交互专家，严格遵守当前项目的 `ailearning_code_standards` 规范。

【系统上下文】
当前项目为 Hybrid RAG 系统，后端基于 FastAPI + DeepSeek 流式输出，前端为原生 JS + CSS 变量体系。

【需求描述】
[在此清晰描述你要增加的具体业务功能，例如：在前端增加一个可以手动调整 Reranker Top-K 阈值的滑动条，并在后端接口接收该参数]

【输出约束】
1. 架构对齐：修改必须符合 MVC/解耦原则，不可将前端 DOM 逻辑写进后端，也不可将大模型逻辑写进路由。
2. 完整性：禁止输出“...”等省略号代码，必须提供可以直接 Copy/Paste 运行的完整修改块。
3. 防御性编程：对于新增加的参数，后端必须通过 Pydantic 进行校验，前端必须有非空/极值拦截，并使用 Toast 提示用户。
4. 样式对齐：前端 UI 必须使用 `var(--bg-card)`、`var(--accent-blue)` 等现有设计系统的 CSS 变量。
```

### 2. 🐛 业务 Bug 排查 Prompt 模板
```text
【角色设定】
你是一名资深的 SRE 与代码审查专家。

【故障描述】
[在此贴出完整的报错 Traceback 栈，或者描述前端出现的具体卡顿/白屏现象]

【近期变更点】
[说明最近动了哪些代码，例如：刚刚升级了 sentence-transformers 库，或者刚加了流式输出逻辑]

【排查要求】
1. 诊断根因：不要急于给代码，先用 1~2 句话点破故障的本质原因（例如环境隔离问题、同步阻塞异步问题）。
2. 给出修复方案：优先给出改动最小、最符合当前项目上下文的修复方案。
3. 补充健壮性：除了修复这个 Bug，请顺手把同类可能导致崩溃的边缘条件（Edge Case）一并加上 try-except 保护。
```

### 3. 🧪 业务单元测试生成 Prompt 模板
```text
【角色设定】
你是一名极度严苛的测试开发工程师。

【测试目标】
请为以下文件/函数编写单元测试：[填写目标文件，例如 hybrid_rag/rag_engine.py 中的 RRF 融合算法]

【测试约束】
1. 测试框架：默认使用 `pytest`。
2. 数据 Mock：对于依赖外部大模型（DeepSeek）或耗时的本地向量模型（CrossEncoder）的方法，必须使用 `unittest.mock.patch` 完美 Mock 掉，保证测试能秒级运行。
3. 覆盖场景：必须包含至少 1 个 Happy Path，1 个边界情况（如两个列表长度不一致的 RRF 融合），以及 1 个异常情况。
```

## 三、 给智能体 (Agent) 的强制纪律
作为 AI 助手，在执行业务逻辑改动时：
- **主动对齐**：当用户的 Prompt 过于简单（如：“加个历史记录功能”）时，你必须在脑海中自动套用上述【新业务需求开发】的完整逻辑，主动考虑存储、UI 变量、后端校验等。
- **防止漂移**：如果用户要求引入类似 Redis、Celery 等大型中间件，必须先发出**架构告警**，评估是否破坏了当前“轻量级离线架构”的初衷，确认后方可实施。
