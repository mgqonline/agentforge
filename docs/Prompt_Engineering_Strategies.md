# 提示词工程 (Prompt Engineering) 核心策略指南

在与大语言模型（LLM）交互时，不同的任务复杂度决定了我们需要使用不同的提示词策略。以下是关于 **Zero-shot (什么都不用)**、**Few-shot (少样本)** 和 **Chain-of-Thought (思维链)** 的能力边界与适用场景。

---

## 1. 什么场景“什么都不用” (Zero-shot Prompting)

**Zero-shot** 指的是直接给出指令，不给任何示例，也不要求模型解释过程，直接要结果。

*   **适用场景**：
    *   **通用自然语言处理**：如中英翻译、文章总结提取摘要、长文润色。
    *   **常识性问答**：例如“解释一下什么是黑洞”、“Python 的列表和元组有什么区别”。
    *   **基础情感分析**：例如“判断这句话是正面还是负面情绪”。
*   **为什么不用**：
    *   现代大模型（如 GPT-4、Claude 3.5、千问 Max）在预训练阶段已经见过了海量的此类任务。它们本身就非常擅长这些。
    *   此时添加复杂的例子或要求它“一步步思考”只会**白白浪费 Token（增加成本和延迟）**，甚至可能因为你给的例子不够好，反而局限了模型的发挥。
*   **最佳实践**：指令必须清晰、直接、角色明确。
    *   *示例*：`你是一个资深编辑，请将以下文本缩写为 100 字以内的摘要，保留核心数据：[文本]`

---

## 2. 什么场景用“少样本学习” (Few-shot Prompting)

**Few-shot** 指的是在提示词中提供 1 个或多个（通常 2~5 个）完整的“输入-输出”对照示例，然后再让模型处理新的输入。

*   **适用场景**：
    *   **极其严格的格式要求**：当你需要输出非常特殊的 JSON 嵌套结构、特定的 CSV 排版，用大段文字解释规则往往不如直接给 2 个例子管用（**Show, don't tell**）。
    *   **私有领域的专有名词映射**：例如医疗缩写分类（将“高血压”映射为“HTN”，将“心衰”映射为“HF”），模型本身不知道你们公司内部的简称。
    *   **特定的语气或风格模仿**：例如让模型模仿你们老板以往写邮件的简短风格、或者特定的公文格式。
*   **核心优势**：
    *   LLM 具有极强的“模式识别”能力（Pattern Recognition）。只要给足例子，它能瞬间进入你划定的“模版”中。
*   **最佳实践**：
    *   给 2-3 个例子往往就能达到极佳效果，给太多（如 20 个）不仅烧钱，还容易让模型“过拟合”，对没见过的特殊情况失去泛化能力。
    *   *示例*：
        ```text
        请把用户输入转化为我们内部的标签体系：
        输入: "这屏幕也太容易划伤了" -> 输出: [质量问题 - 屏幕材质]
        输入: "快递等了三天还没发货！" -> 输出: [物流问题 - 发货延迟]
        输入: "电池用了半天就没电了" -> 输出:
        ```

## 3. 什么场景用“思维链” (Chain-of-Thought / CoT)

**CoT** 的核心是强迫模型在给出最终答案前，先把**推理过程**打印出来（最经典的咒语：`Let's think step by step`，或者要求 `先在 <thinking> 标签内思考，再给出 <answer>`）。

*   **适用场景**：
    *   **数学计算与逻辑推理**：比如鸡兔同笼、时间倒推计算。
    *   **Agent 智能体的决策（核心应用！）**：在 LangGraph 中，当 Agent 需要决定“现在是该搜索网页、还是该查数据库、还是该直接回答”时，必须用 CoT 让它分析利弊再调用工具。
    *   **代码 Debug**：让模型找出一大段代码中的潜在 Bug。
*   **底层原理解析（为什么 CoT 会有用？）**：
    *   大模型是**单向自回归**的，它只能根据前面吐出来的字，预测下一个字。
    *   如果你直接逼它说出答案，它脑子里并没有“暂存草稿纸”的空间。
    *   使用 CoT 时，大模型吐出来的那些**“思考过程的字符”，实际上就充当了它的“工作内存（Working Memory / 草稿纸）”**。它看着自己刚才写下的中间推导步骤，就能推导出正确的下一个步骤，最终得出正确答案。
*   **最佳实践**：
    *   对于高度复杂的任务，可以将 Few-shot 和 CoT 结合使用（即 **Few-shot CoT**：在例子里不仅给出输入和输出，连带思考过程也作为例子写出来）。

---

## 总结：如何做工程选择？

1. **先试 Zero-shot**：能用一句清晰指令搞定的，绝不搞复杂。这是最省钱、最快的。
2. **格式乱了/对齐不准？加上 Few-shot**：当发现模型总是输出你不想要的格式或类别时，丢两个例子进去，立竿见影。
3. **逻辑错了/胡说八道？加上 CoT**：当发现模型遇到复杂问题就开始瞎编（算错数字、调错工具）时，强迫它“先解释原因，再给出结论”。
