# FastAPI 在 AI 工程中的高级架构指南

为什么当今几乎 100% 的 AI 应用（如 LangServe、各大公司的 Agent 接口层）底座全部放弃了 Django / Flask，转向了 **FastAPI**？

除了原生支持 Python 的高并发异步 `async/await`，它的这四大杀手级高级特性是你能够独立接手甚至从零搭建 AI 项目架构脚手架的关键。

结合 `12-fastapi-advanced/app.py` 的实战演示，我们来拆解这四个高级特性解决了什么工业痛点：

## 1. `Lifespan` 生命周期管理 (取代 `startup/shutdown` 事件)

*   **AI 痛点**：在做模型部署时，我们需要加载动辄几个 GB 大小的权重文件到显存中。如果你把加载代码直接写在文件最顶端（全局变量），会导致各种测试环境初始化地狱；如果在每次请求来时再加载，每个请求都要等一分钟。
*   **现代解法**：`Lifespan` 机制。利用 `@asynccontextmanager`，以极其优雅的 `yield` 关键字将应用劈成两半：
    *   `yield` 之**前**的代码：服务器挂载端口前执行，安心地在这里把大模型加载到字典或显存。
    *   `yield` 之**后**的代码：服务器收到终止命令（Ctrl+C）时执行，在这里安全地清空显存（`cuda.empty_cache()`），防止显存泄漏。

## 2. 嵌套 `Depends` 依赖注入树

*   **痛点**：你有一个接口，需要依次判断：1. Token有无过期 -> 2. 从 Token 提取 UserID -> 3. 判断该 UserID 是否充值了 VIP 余额。如果你在每个接口里写一堆 `if-else`，代码会恶心到无法维护。
*   **神级解法**：FastAPI 的绝对核心灵魂机制 `Depends`。它不是简单地执行一个函数，而是自动构建出一棵“依赖树”：
    *   函数 C 依赖函数 B，函数 B 依赖函数 A。
    *   当你的路由接口里写了 `db = Depends(C)` 时，FastAPI 会聪明地逆向追溯，先跑 A，把 A 的结果喂给 B，再把 B 的结果喂给 C。整个认证和参数组装过程毫无侵入感！

## 3. 中间件 `@app.middleware("http")`

*   **痛点**：老板要求你统计全站所有 100 多个 API 接口的响应耗时，并在 Response Header 里返回给前端；或者要求你做一个全局黑名单系统拦截指定 IP。
*   **解法**：绝不要去修改具体的路由代码。写一个中间件拦截在最外层。请求来时，先经过中间件的漏斗；响应走时，再经过中间件过滤。

## 4. `BackgroundTasks` 轻量后台任务

*   **AI 痛点**：Agent 大脑要执行一套复杂的思考链路（例如查资料、推演、写论文），耗时极长。HTTP 协议有一个天生的弱点：如果服务端几十秒不返回数据，前端的浏览器连接池就会自动判定超时 (Timeout) 崩溃。
*   **解法**：
    *   如果是海量的高并发长任务，工业界会用重型武器：`Celery` + `Redis` / `RabbitMQ` 消息队列。
    *   但对于日常 80% 的中小型场景，引入 Celery 显得太笨重。FastAPI 自带了轻量武器 `BackgroundTasks`。
    *   在接口被调用时，你只需极速告诉大模型开始干活，然后**瞬间返回 HTTP 200 状态码（"您的任务已受理"）**，把重活塞进后台线程。这是 AI Web 接口响应防崩溃的保底救命绝招！
