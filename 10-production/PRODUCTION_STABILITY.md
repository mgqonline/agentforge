# 端到端生产级实战：稳定性与成本控制

在把大模型推向生产环境（Production）时，仅仅“能跑通”是远远不够的。生产环境中有两只拦路虎：**暴涨的 Token 费用账单** 和 **不稳定的上游 API 服务**。

## 一、Token 精细化管理

### 痛点：
多轮对话中，如果一直把所有的历史记录无脑追加发给模型（`[Msg1, Msg2, ..., Msg100]`），不仅会导致大模型遗忘最新指令（Lost in the Middle 现象），还会因为每次都发送冗长的历史记录而造成巨大的 Token API 费用浪费，甚至触发大模型单次交互的 Max Token Limit（爆显存）。

### 策略：
1. **滑动窗口裁剪 (Sliding Window)**：就像行车记录仪一样，我们只保留最近 `N` 轮对话。
2. **系统指令隔离保底**：不管怎么裁，最初设定 AI 人设和核心红线的 `SystemMessage` 绝对不能丢。
3. **向量化压缩 / 摘要化 (Summarization)**：当历史记录不得不丢弃时，可以开一个异步后台任务，把很久以前的废话总结成一句“摘要记忆”，或者灌入向量数据库 (RAG 架构)。

## 二、限流熔断与降级预案

### 痛点：
第三方大模型 API 会频繁遇到以下问题：
*   **Rate Limit (被限流)**：比如并发数超过限制（`429 Too Many Requests`）。
*   **Timeout (超时)**：比如网络波动或大模型算力资源吃紧，半天不吐字。
*   **Service Unavailable (服务宕机)**：直接 500/502 报错。

如果在你的业务代码里不接管这些异常，用户的页面就会一直转圈然后白屏崩溃。

### 降级策略 (Fallback)
标准的系统降级分三步走：
1.  **主力线路重试 (Retry + Exponential Backoff)**：遇到网络抖动先原地重试 2 次，采用指数退避机制（等 1s 试一次，再等 2s 试一次），防止把上游打瘫。
2.  **备胎降级 (Model Fallback)**：主力 `gpt-4o` 如果连续超时挂掉，立刻平滑切换调用备用通道（比如价格更便宜但稳定的 `gpt-4o-mini` 甚至别的厂家的模型）。用户只会觉得稍微慢了一秒，但依然拿到了有效的回答。
3.  **终极静态兜底 (Static Fallback)**：当备胎也连不上（比如机房光缆全断了），代码捕获终极异常，向前端抛出预设好的静态文案：“对不起，由于访问火爆，系统正在排队中，请稍后再试”。永远不要把 500 堆栈信息展示给 C 端用户。
