# Python 高级特性在 AI 工程中的实战指南

对于一般的脚本编写，你也许不需要掌握太深奥的 Python 语法。但在构建 AI 工程（尤其是开发复杂的 Agent、高并发的爬虫或 API 服务）时，读懂第三方库源码和熟练使用高级特性是区分“新手”与“资深工程师”的分水岭。

结合 `advanced_python_demo.py` 的代码演示，我们来看这些特性究竟解决了什么业务痛点：

## 1. 装饰器 (Decorators) 与 `functools.wraps`
* **应用痛点**：调用 LLM 大模型接口时，经常会因为网络波动、账号限流等问题抛出异常。如果每次都在代码里写 `try...except...for` 循环，代码会像意大利面条一样极其臃肿恶心。
* **技术解法**：编写一个 `@retry_llm_call` 装饰器，优雅地将其挂在任何需要重试的网络请求函数上方。
* **核心坑位**：一定要在装饰器内部使用 `@functools.wraps(func)`！如果不加，被装饰的函数的名字（`__name__`）就会变成 `wrapper`，它的 `docstring` 也会丢失。在 LangChain 这种需要通过反射获取函数注释来自动生成 System Prompt 的框架中，如果不加 `wraps`，大模型将完全不知道这个工具是干什么用的！

## 2. 上下文管理器 (`@contextmanager`)
* **应用痛点**：每次打开数据库连接或文件流时，如果中间报错了，忘记写 `finally` 关闭连接，就会导致服务器连接数打满宕机。
* **技术解法**：不使用繁琐的类的 `__enter__` 和 `__exit__` 方法，而是通过 `contextlib` 包里的 `@contextmanager` 装饰器结合 `yield` 关键字，只需几行代码就能写出极其优雅的资源管理和耗时统计工具包。

## 3. 生成器 (Generator) 与流式输出
* **应用痛点**：当大模型要输出一篇 2000 字的研报时，如果等大模型全部生成完毕再通过 HTTP 响应给用户，用户盯着白板页面往往需要等上几十秒，体验极差。
* **技术解法**：使用 `yield` 关键字，每当大模型预测出一个单词 (Token)，就立刻顺着 HTTP 长连接推给前端页面，实现打字机效果。这在 AI 领域被称为 Streaming，是现代 AI 产品必备的基建。

## 4. `asyncio` 高并发 (`gather` vs `as_completed`)
* **应用痛点**：Agent 接收到一个需要“读 3 篇极长文档”的任务。如果一篇篇读，大模型要花费 30 秒。
* **技术解法**：通过 `async/await`，我们可以并发向大模型发射 3 个网络请求。
  * `asyncio.gather`：并行派发所有任务，并且**严格按照你派发的顺序返回结果数组**。极其适合后方还需要对数据进行严格规整拼接的场景。
  * `asyncio.as_completed`：并行派发，但**谁先做完，就先 yield 返回谁**！如果你在做一个前端面板，短文档瞬间解析完就瞬间展示给用户，长文档在后面慢慢转圈，用户体验达到极致。

## 5. `dataclass` 与 Pydantic
* **应用痛点**：由于大模型本质是语言模型，它生成的参数总是不可靠的！比如你要求工具必须传入数字类型的 `age`，大模型极有可能偏偏给你传一个字符串 `"二十岁"` 或者传个负数。
* **技术解法**：
  * `@dataclass`：对于我们代码内部极其可控的系统变量传递（如 LangGraph 里的 `State`），用 dataclass 写法极其轻量优美。
  * `Pydantic BaseModel`：这是**整个 AI Agent 领域的绝对核心数据规范**！当我们接收来自外部、或来自大模型生成的不可靠 JSON 字符串时，Pydantic 会筑起一道钢铁防线：一旦数据类型不对、范围越界，它会立刻抛出极度详尽的 `ValidationError`。然后，框架会捕获这个 Error，**原封不动地发回给大模型让它自我反思并重新生成**！
