# 多模态 RAG (图像处理) 原理架构图

## 方案一：描述法 (Image Captioning) - 最成熟、最通用
这种方案的核心是“将视觉问题转化为文本问题”。

### 1. 索引阶段 (Indexing)
1. **输入**: 一张架构图 `architecture.png`。
2. **分析**: 调用 Vision 模型（如 GPT-4o, Claude 3.5V, 或本地 Qwen-VL）。
   - *Prompt*: "请详细描述这张图片的内容，包括文字、流程方向和核心组件。"
   - *输出*: "这是一张 LangGraph 架构图，展示了从 Agent 到 Tools 的循环逻辑..."
3. **存储**:
   - **向量**: 存储“描述文本”的 Embedding。
   - **元数据 (Metadata)**: 存储原始图片的路径 `{"image_path": "path/to/architecture.png"}`。

### 2. 检索阶段 (Retrieval)
1. **查询**: "这个项目的图里是怎么定义 Agent 的？"
2. **搜索**: 在向量库中匹配“描述文本”。
3. **命中**: 找到描述中最匹配的片段，并提取关联的 `image_path`。

### 3. 生成阶段 (Generation)
1. **增强**: 将“图片描述”作为上下文喂给 LLM。
2. **回复**: "根据架构图显示，Agent 被定义为..."

---

## 方案二：联合向量空间 (Joint Embedding) - 响应最快、更底层
这种方案使用专门的模型（如 OpenAI CLIP 或 Google SigLIP）。

### 核心原理
- **CLIP 模型**: 它在训练时被喂了数亿对“图片+文字”。
- **神奇特性**: 它能让“猫的图片”生成的向量，和“猫这个词”生成的向量，在空间里离得非常近。

### 1. 索引阶段
- 直接将图片通过 CLIP 变成一个 512 或 768 维的向量。
- 存入向量数据库，不需要任何文字描述。

### 2. 检索阶段
- 用户输入文字 -> 经过 CLIP 变成向量。
- 在数据库中进行“以文搜图”。

---

## 两种方案对比

| 特性 | 描述法 (Captioning) | 联合嵌入 (CLIP) |
| :--- | :--- | :--- |
| **理解深度** | **极高**（能看懂流程图里的逻辑） | **中等**（擅长识别物体，不擅长逻辑） |
| **检索速度** | 较慢（需要先生成描述） | **极快**（直接向量搜索） |
| **成本** | 较高（调用 Vision 模型贵） | 较低（本地模型即可完成） |
| **适用场景** | 复杂报表、架构图、文档插图 | 搜风景照、产品图、以图搜图 |
